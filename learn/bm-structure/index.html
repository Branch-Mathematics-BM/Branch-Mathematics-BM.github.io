Architecture

Branches, Leaves, Trees, Passports and Roots

Branch Mathematics carries one problem through multiple mathematical branches without erasing their native structure. Branches do the mathematics, Interactions connect lawful outputs, Leaves record results, the Tree assembles the problem state, Passports declare receiver obligations, and Roots are receiver-facing exports.

Short version: these are organizational roles, not replacements for algebra, topology, PDEs, probability, geometry, operator theory, or any other native mathematics used inside a Branch.

Why BM needs an architecture at all

Many serious problems require more than one mathematical viewpoint. A PDE may need functional analysis, a boundary interface may need operator theory, a network coupling may need graph structure, and the final receiver may impose a different task geometry.

The challenge is not merely to use several mathematical fields. It is to connect them without silently identifying structures that are not actually equivalent.

Branch Mathematics keeps each mathematical sector native until a lawful interaction earns the connection.

Branch

Core role

A Branch is a lawful mathematical focus.

A Branch carries part of the problem in its native mathematics. It may use its own state space, laws, topology, operators, admissibility conditions, approximations, and proof techniques.

A Branch is not required to look like another Branch.

For example, one Branch may be a finite graph problem while another is an infinite-dimensional PDE problem. BM does not force both into the same vocabulary simply to make the framework visually uniform.

preserve native structure first; connect branches only through declared lawful relations

When should a problem split into distinct Branches?

A split should be mathematically compelled, not decorative.

In the current BM criterion, a compelled split occurs when there is no admissible embedding into one shared structure that preserves the laws and distinctions required by the problem.

no admissible common embedding preserving required laws/distinctions ⇒ distinct Branches

Simply placing two objects into a disjoint union does not solve the problem. The shared structure must preserve the actual mathematics that matters.

Interaction

Core role

An Interaction is a lawful connection between Branch outputs or obligations.

Interactions determine when a result from one Branch may constrain, feed, alter, test, or combine with another Branch.

An Interaction does not automatically inherit every law from either Branch.

BM firewall: interacting mathematical sectors do not automatically inherit one another's laws.

The Interaction must state what is actually transported across the connection.

Leaf

Core role

A Leaf is a Branch result available to the larger problem.

A Leaf can be a theorem, invariant, obstruction, bound, quotient, profile, repair certificate, operator relation, or another lawful output produced inside a Branch.

The important point is provenance: a Leaf should remain tied to the Branch and assumptions that produced it.

A Leaf carries a result outward without pretending the rest of the Tree automatically inherits the entire native Branch.

Tree

Core role

The Tree is the assembled mathematical state of the problem.

It records the active Branches, their Leaves, lawful Interactions, unresolved conflicts, receiver obligations, and the current state of the overall problem.

The Tree is not one giant equation. It is the organized total state after respecting the distinctions between Branches.

A Tree can contain:

1
Compatible results Leaves that lawfully combine or reinforce one another.
2
Certified obstructions Places where assumptions, realizations, or Branch outputs cannot be reconciled under the current contract.
3
Open obligations Requirements that remain unresolved before the receiver can accept an export.
4
Provenance Where each result came from and what assumptions support it.

Passport

Receiver contract

A Passport declares what the receiver requires.

A Passport can specify tasks, contexts, tolerances, horizons, admissible continuations, interface obligations, realization requirements, and acceptance conditions.

The Passport is what makes BM's notion of necessary distinction precise.

A distinction matters when removing it would violate some declared obligation in the Passport.

Passport changes ⇒ required distinctions may change

Why Passport comes before Root

A Root is not simply whatever output the Tree happens to produce.

The receiver must declare what counts as acceptable before an export can be certified against it.

receiver obligations → acceptance test → Root

This is why BM treats Root as receiver-facing rather than foundational.

Response

Receiver-facing map

A Response is what the assembled system presents to the declared receiver.

It may be exact or approximate, static or dynamic, deterministic or stochastic, algebraic or physical, depending on the Branches and Passport involved.

The Response is judged relative to the Passport. It is not automatically a Root.

Root

Accepted export

A Root is a receiver-facing export that satisfies the declared acceptance conditions.

Root is therefore an endpoint of a lawful BM workflow, not the primitive object from which the entire mathematics grows.

Tree → Response → receiver acceptance → Root

A different receiver can accept a different Root from the same underlying Tree because the Passport can differ.

Root does not mean “fundamental truth”

The word is project-defined. It should not be imported from graph theory, algebraic geometry, polynomial roots, or ordinary tree terminology.

In BM, a Root is simply the accepted receiver-facing export under the declared Passport.

BM terminology is project-defined. Do not silently import standard meanings when a BM definition is explicitly declared.

A simple worked architecture

Suppose the problem is a PDE-controlled network with a receiver that needs one scalar output within a tolerance.

One possible BM decomposition is:

1
PDE Branch Analyze the field evolution and derive a boundary response operator.
2
Network Branch Analyze how boundary outputs couple into the finite network.
3
Approximation Branch Determine whether a reduced interface satisfies the allowed error tolerance.
4
Leaves Export the PDE port operator, network constraint, and approximation certificate.
5
Interactions Check that the reduced port still preserves the coupling distinctions required by the network.
6
Tree Assemble the compatible results and any remaining obstruction.
7
Passport and Root Test the final response against the receiver's task and tolerance, then export the accepted Root.

What happens when Branches disagree?

BM does not require disagreement to be hidden or averaged away.

If two Branch obligations cannot be simultaneously realized under the current contract, the Tree should preserve the collision as an obstruction.

incompatible obligations → Certified Obstruction, not silent collapse

Repair can then alter the representation, contract, interface, realization, or another admissible part of the architecture.

Pairwise compatibility is not enough

Multiple Branches can be pairwise compatible while still lacking one global realization that satisfies them all simultaneously.

BM firewall: pairwise local compatibility does not imply global realizability.

This matters whenever the Tree glues together several local sectors, interfaces, or constraints.

Branches are not departments

A Branch is not just a label like “topology Branch” or “PDE Branch.” A useful Branch must be mathematically motivated by the actual structure of the problem.

Arbitrary subdivision adds bureaucracy without mathematical value.

Branches exist because the problem requires distinct lawful mathematical structure, not because BM wants more boxes in a diagram.

Leaves are not conclusions without scope

A Leaf should carry the assumptions and scope under which it is valid.

A local PDE estimate does not automatically become a global theorem about the full Tree. A quantum algebraic relation does not automatically become a physically realizable channel. A finite-state result does not automatically extend to an infinite-dimensional sector.

Leaf provenance must survive export

The Tree is not automatic unification

BM does not assume that every Branch ultimately collapses into one common mathematics.

A Tree can legitimately contain several distinct structures connected only where lawful interactions have been established.

Unification by assumption

Force every sector into one representation first and resolve mismatches afterward.

BM assembly

Preserve native sectors first and admit only the cross-sector identifications that can be justified.

How this connects to the BM pipeline

The organizational roles sit inside the larger foundation:

Specify → Distinguish → Descend → Synthesize → Realize → Quantify

A more expanded view is:

native problem → Passport → required distinctions → Branches → lawful Interactions → Leaves → Tree → Response → Root

The exact order can vary by problem, but the discipline remains: native mathematics, receiver obligations, distinction preservation, lawful interaction, realization, and provenance must stay visible.

Status discipline

The public site should also tell readers whether a result is part of the canonical foundation, an internally verified development, an imported classical result, a candidate, a firewall, or an open problem.

BM uses explicit status labels so organizational language does not accidentally make every statement look equally established.

Tag Meaning
SC Source-certified in the canonical material
RP / CH-V Internally proved or hardened during review
CH-C Candidate development
CI Classical/imported mathematics
BM-SYN BM synthesis or placement of established ingredients
FW Firewall or counterexample
OPEN Open problem

The key idea

Branch Mathematics is not a vocabulary pasted over existing mathematics. Its roles exist to preserve native mathematical sectors, control their interactions, track provenance, and determine what can lawfully reach a receiver.

Once these roles are clear, the reference section and the long-form Book become much easier to read.
