Task-Specific Representations

A task-specific representation preserves the distinctions a declared receiver actually needs. It does not automatically preserve every native difference in the system.

Short version: the same native system can have several different lawful reduced representations because different tasks require different distinctions.

The same system can support different lawful reductions

Suppose a native state contains many variables. One receiver may ask for parity, another may ask for the number of active components, and a third may demand full reconstruction.

Those tasks do not require the same distinctions.

There is no reason to require one representation to preserve information that its declared receiver will never lawfully use.

Branch Mathematics makes this dependence explicit instead of treating a representation as universally “good” or “bad.”

The exact factorization test

Let:

R : X → Q

be a representation of the native state space X, and let:

T : X → Y

be the declared task.

The representation is exactly sufficient when the task factors through the representation:

T = T̄R

for some map T̄ : Q → Y.

Equivalently:

ker(R) ⊆ ker(T)

Whenever the representation merges two native states, the task must also treat those states as identical.

A concrete example

Three different receivers

Let the native state be a binary vector:

x = (x₁,…,xₙ) ∈ {0,1}n

Now compare three tasks:

Task Required distinction Possible exact representation size
Parity Even versus odd total 2 states
Count 0,1,…,n active bits n+1 states
Full reconstruction Every native bit pattern 2n states

The native system is identical in all three cases. Only the receiver changes.

Task-relative does not mean arbitrary

A common misunderstanding is that if representation depends on the task, then one can choose any reduction one likes.

That is not the BM position.

Once the task is declared, the representation must satisfy a mathematical condition. The receiver chooses the contract; the mathematics determines what that contract permits.

declared task first → admissible quotient second

This is why Passports exist

A task by itself may not be enough to specify the real obligation.

The receiver may also care about:

1
Future dynamics The representation may need to remain sufficient after lawful evolution.
2
Context Different environments or peer subsystems may reveal different distinctions.
3
Tolerance The receiver may allow bounded approximation rather than exact equality.
4
Implementation class A quotient may need a smooth, local, stochastic, quantum, or otherwise admissible realization.
5
Receiver acceptance The final export must satisfy the receiver-facing contract, not merely an internal mathematical condition.

BM packages these declared obligations into a Passport.

Current task versus future task

A representation sufficient for the current task can still be too coarse for future evolution.

Current task

Merge states when they give the same response now.

Future-aware task

Keep states separate when a lawful future can make their task responses diverge.

This leads directly to dynamic closure and temporal exactification.

current sufficiency does not imply dynamic sufficiency

Context can change the quotient

Suppose a subsystem exports a compressed state to another subsystem. Whether two local states are safely mergeable may depend on what external context the peer subsystem can supply.

BM therefore uses contextual equivalence of the form:

x ∼ x′ ⇔ B(x,c)=B(x′,c) for every allowed context c

If two states agree only under one context but differ under another allowed context, a portable interface must preserve the distinction.

Portable representations must survive every context allowed by the contract, not merely the deployment used during one test.

Deployment-specific and portable representations are different

A representation designed for one known environment can sometimes be much smaller than one that must remain valid across many environments.

Representation type What it must survive
Deployment-specific The declared fixed peer context or environment
Portable Every allowed context in the Passport

The gap between them is a portability surcharge.

Interfaces are task-specific representations

A subsystem boundary is one of the most important places where task-specific representation appears.

The full internal state of a subsystem may be enormous, but the neighboring subsystem may only need a small interface variable.

internal state → task-relevant boundary profile → receiver

The minimal exact portable interface identifies two subsystem states only when every allowed external context produces the same declared global response.

This is one reason BM applies naturally to domain decomposition, network cuts, distributed systems, PDE ports, and quantum carriers.

Approximate task-specific representation

When tolerance is positive, equality is replaced by bounded response error.

Instead of exact quotient classes, one seeks cells whose receiver-visible profiles fit inside admissible radius-ε balls.

w(ε) = log₂ N(ε)

where N(ε) is the minimum number of task-profile representatives needed at tolerance ε.

The resulting width is task-, context-, metric-, and tolerance-dependent.

One native system can have several semantic widths

Consider the same physical or mathematical system under three Passports:

Passport Receiver obligation Expected representation burden
P₁ Single scalar output Potentially small
P₂ Finite-horizon trajectory Potentially larger
P₃ Full-state reconstruction Potentially much larger

There is no contradiction. They are different receiver problems.

Task-specific does not mean state-independent

BM is not saying the task can ignore native mathematics.

A valid representation still depends on what the native dynamics, topology, algebra, geometry, locality, and physical realization allow.

Receiver-relativity does not override native law. A Passport declares what must be preserved; it does not grant permission to violate the mathematics of the underlying sector.

A representation can be sufficient but unrealizable

Suppose an exact quotient exists abstractly. The quotient may still fail to admit the required implementation.

Examples include:

A
Topological obstruction The quotient exists as a set but cannot be embedded into the desired Euclidean dimension.
B
Smooth obstruction The required identification may fail to admit a global smooth realization.
C
Distributed obstruction A centralized quotient may not decompose into the required local interfaces without extra width.
D
Quantum physical obstruction An algebraic carrier may fail to correspond to a CPTP physical realization.
sufficiency and realization are separate stages

Task-specific representation in PDEs

For a PDE, the native state may be an entire field u(x), while the receiver only needs a boundary flux, integrated quantity, sensor trace, or finite-horizon output profile.

In that case, the receiver-visible profile rather than the entire field determines the semantic burden.

P(u) = declared receiver-visible PDE response

Two fields can be very different internally and still belong to the same exact or approximate task class if their declared profiles agree.

Task-specific representation in quantum systems

The same distinction appears in quantum information.

Recovering an entire quantum state is stronger than recovering one observable, one operator system, or one task algebra.

A code can therefore fail full-state recovery while remaining exact for a weaker declared observable task.

full-state recovery requirement ⊃ task-observable recovery requirement

BM treats these as different Passports rather than calling the code simply “working” or “broken.”

Task-specific representation in networks

In a network, a cut may not need to transmit every upstream variable. It needs enough distinction to determine the downstream task under the allowed future context.

The centralized semantic requirement can be smaller than the cost of realizing it across multiple local routes.

semantic content + locality constraints = realized interface cost

The BM design procedure

A task-specific representation should be built in the following order:

1
Declare the native problem State the actual mathematical system before compression.
2
Declare the Passport Specify task, receiver, context, horizon, tolerance, and realization requirements.
3
Determine required distinctions Identify which native differences can change a declared response.
4
Construct the quotient or cover Build the coarsest exact or admissible approximate representation allowed by the contract.
5
Test dynamics and interactions Check that the representation remains lawful under future evolution and cross-branch coupling.
6
Realize it natively Verify that the abstract representation has an admissible implementation in the required category.
7
Quantify the cost Measure width, error, robustness, locality surcharge, memory, or other relevant price.

The key idea

A representation is not good because it is small. It is good when it is as small as the declared task allows without destroying distinctions the system must still use.

That is the role of task-specific representation inside Branch Mathematics.
