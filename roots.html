Roots

The receiver-relative downstream-use layer of Branch Mathematics: how a Response is exported, when an export becomes admissible for a specified receiver, how Root information is reused, and how ordinary re-entry is separated from candidate Rooting, Rebranching, and Seed structures.

1. What a Root Is

A Root is an exported mathematical result that satisfies the declared receiving conditions of a specified downstream mathematical context.

\[ \boxed{ r \text{ is a Root for receiver }B_r \iff r \in \operatorname{Acc} (\mathcal P_R^{B_r}). } \]

Root is therefore a receiver-relative structural role. It is not a new algebraic species of object.

\[ \boxed{ \text{Root} = \text{receiver-admissible exported result}. } \]
  • A Response is not automatically a Root.
  • A Root is not automatically recursive.
  • A Root does not automatically create a new Branch.
  • A Root does not create a conservation law.
  • A Root does not automatically converge, stabilize, or repeat.

2. Response, Export, Root, and Re-entry

\[ \boxed{ \text{Tree} \longrightarrow \text{Response} \xrightarrow{E_r} \text{exported candidate} \xrightarrow{\mathcal P_R^{B_r}} \text{Root for }B_r \longrightarrow \text{lawful re-entry or terminal use}. } \]
Role Meaning
Tree A Configuration with a selected lawful realization and required context.
Response Typed output of the realized computation.
Export Receiver-directed transformation of the Response.
Root Export accepted by the specified receiver Passport.
Re-entry Lawful downstream use of the accepted export.
These roles may all involve the same underlying mathematical value. BM is tracking its role in the larger problem, not manufacturing new objects.

3. Root Role vs Mathematical Carrier

Let \(r\) be a mathematical object. BM may record

\[ \boxed{ r \models_C \mathrm{Root}_{B_r}. } \]

This means that \(r\) satisfies the Root conditions in Configuration \(C\) relative to receiver \(B_r\).

The same object may also be:

\[ r \models_C \mathrm{Leaf} \land \mathrm{Response} \land \mathrm{Root}_{B_r}. \]
The terms Leaf, Response, and Root identify different participation roles. They do not require three copies of the mathematical value.

5. Typed Root Record

Root is a role, not an intrinsic tuple. When a registry record is useful, one may record:

\[ \boxed{ \mathfrak R_{B_r}(r) = \left( \tau_r, Y, r, B_r, D_{\mathcal P_R}, \mathcal P_R^{B_r}, \mathcal I_R \right). } \]
\(\tau_r\) Native mathematical type of the exported object.
\(Y\) Carrier of the Response/export.
\(r\) The actual exported mathematical object.
\(B_r\) The receiver for which Roothood is asserted.
\(D_{\mathcal P_R}\) Applicability domain of the Root Passport.
\(\mathcal P_R^{B_r}\) Instantiated receiver obligations.
\(\mathcal I_R\) Receiving Interface information.
The record is organizational. Other sectors may use a richer or different native representation.

6. Root Formation

Production of an output establishes a Response. Root formation is a separate receiver test.

\[ T \xrightarrow{\mathcal E} Y, \qquad E_r: D_{E_r} \subseteq Y \to \mathcal R_r, \]
\[ r=E_r(Y). \]

Root formation requires:

\[ \boxed{ r \in \operatorname{Acc} (\mathcal P_R^{B_r}). } \]
\[ \boxed{ \text{Response production} \neq \text{Root formation}. } \]

7. Root Passport Applicability

Before a Root Passport can accept or reject an export, the export must lie in its applicability domain.

\[ \operatorname{Acc} (\mathcal P_R^{B_r}) \subseteq D_{\mathcal P_R^{B_r}}. \]
Case Meaning
\[ r \notin D_{\mathcal P_R^{B_r}} \] The Root Passport is not applicable. The export has the wrong type/domain for this Root gate.
\[ r \in D_{\mathcal P_R^{B_r}} \setminus \operatorname{Acc} (\mathcal P_R^{B_r}) \] The Root Passport applies but rejects.
\[ r \in \operatorname{Acc} (\mathcal P_R^{B_r}) \] The Root Passport applies and accepts.
\[ \boxed{ \text{wrong Root-candidate type} \neq \text{valid candidate that fails its gate}. } \]

8. Root Admissibility

In Set-like sectors, the receiver-admissible Root region may be written as

\[ \boxed{ A_R(B_r) = \operatorname{Acc} (\mathcal P_R^{B_r}). } \]

Typical obligations may involve:

  • type;
  • domain;
  • regularity;
  • law or regime;
  • receiver constraints;
  • Interface compatibility;
  • witness or coupling data;
  • required invariants;
  • future-use information.
Some sectors use predicates, subobjects, cones, relations, operator domains, kernels, or other native admissibility structures instead of a literal subset.

9. Root Passport

A Root Passport is the receiver's instantiated obligation structure for lawful downstream use.

It may contain:

  • type and units;
  • law/regime context;
  • required Interface data;
  • witness or coupling conditions;
  • admissibility certificates;
  • Task-relevant distinctions;
  • continuation information;
  • native invariant obligations;
  • quantitative error bounds.
The visible value \(r\) need not literally encode every item in the Root Passport, provided the required information remains lawfully available to the receiver.

10. Root Passport Sufficiency

In exact deterministic semantics, let

\[ P_R: A_R(B_r) \to Q_R \]

be the Root Passport representation and

\[ T_R: A_R(B_r) \to W \]

a later receiver Task.

Exact sufficiency means:

\[ \boxed{ T_R = \widetilde T_R \circ P_R, \qquad \widetilde T_R: P_R(A_R(B_r)) \to W. } \]

Equivalently:

\[ P_R(r) = P_R(r') \Longrightarrow \boxed{ T_R(r) = T_R(r'). } \]
Root Passport sufficiency is receiver- and Task-relative.

11. Root Status Is Receiver-Relative

\[ \boxed{ r \text{ Root for }B_1 \not\Rightarrow r \text{ Root for }B_2. } \]

Example:

\[ r=8, \]
\[ A_R(B_1) = [0,10], \qquad A_R(B_2) = [0,5]. \]

Therefore:

\[ 8 \in A_R(B_1), \qquad 8 \notin A_R(B_2). \]
Nothing about the scalar \(8\) changed. Only its receiver-relative role changed.

12. Roothood Is Not Transitive

Suppose a Response contains

\[ Y=(x,y). \]

Receiver \(B_1\) needs only \(x\), so

\[ E_1(Y)=x \]

is sufficient for \(B_1\).

A later receiver \(B_2\) needs

\[ x+y. \]

The previous Root \(x\) cannot determine this quantity.

\[ \boxed{ \text{Root for }B_1 \not\Rightarrow \text{Root for every descendant receiver}. } \]

13. Root Role Lifetime

Root status can depend on receiver, context, regime, time, or active obligations.

\[ \boxed{ r \in A_R (B_r,\lambda,t,c). } \]

A mathematical value may remain unchanged while its Root role changes.

Root is not a permanent intrinsic label attached to an object forever.

14. Root Reuse

A Root may participate in later mathematics only when the actual later Operation or Interaction accepts it.

\[ J: D_J \subseteq A_R(B_r) \times A_B \to Z. \]
\[ \boxed{ (r,b) \in D_J. } \]
Passing one Root gate does not waive later domain, Interface, Passport, law, or coupling requirements.

15. Root Re-entry

Export and re-entry are separate mathematical steps.

\[ E: A_R(B_1) \to Y_E, \]
\[ Q: D_Q \subseteq Y_E \to Z. \]

The actual re-entry domain is

\[ \boxed{ D_{Q\circ E} = \{ r \in A_R(B_1): E(r) \in D_Q \}. } \]
\[ \boxed{ \text{successful Root export} \not\Rightarrow \text{successful later re-entry}. } \]

16. Exact Root-Passport Transfer

Root-Passport transfer does not require a new independent Root theory. In exact deterministic semantics it is ordinary Interface/factorization mathematics.

Let

\[ P_S: X \to Q_S, \]
\[ F: X \to A_R(B_r), \]
\[ P_R: A_R(B_r) \to Q_R. \]

Exact transfer through \[ \tau: P_S(X) \to Q_R \] requires:

\[ \boxed{ P_R \circ F = \tau \circ P_S. } \]
Stochastic, relational, approximate, or quantum transfers require their own native semantics.

17. Root Information Loss

A Root representation may be sufficient for one receiver and insufficient for a later one.

\[ P_R(r) = P_R(r') \]

while

\[ \boxed{ T_2(r) \neq T_2(r'). } \]

The representation then loses a distinction required by the later Task.

\[ \boxed{ \text{earlier Root sufficiency} \not\Rightarrow \text{later receiver sufficiency}. } \]

18. Root Repair

If Root Passport \(P_R\) is insufficient for later Task \(T_R\), a refined representation may add information

\[ q: A_R(B_r) \to Z. \]

yielding

\[ \boxed{ (P_R,q): A_R(B_r) \to Q_R \times Z. } \]

Repair succeeds when

\[ \boxed{ T_R = \widehat T_R \circ (P_R,q) } \]

on the realized refined image, and when the repair belongs to the declared admissible repair class.

Repair may introduce new cost, privacy, complexity, Interface, or stability obligations.

19. Repair Revalidation

If repair changes data in region \(S\), the affected semantic dependency closure is

\[ \boxed{ \operatorname{Cl}_{\mathfrak D_C}(S). } \]

Every dependent Root certificate must then be:

  1. recomputed; or
  2. shown invariant under the repair.
\[ \boxed{ \text{upstream repair} \not\Rightarrow \text{Root status remains certified}. } \]

20. Root Observability

A Root can be downstream-admissible without being directly observable in full.

\[ H: A_R(B_r) \to Y. \]

For Root Task \(T_R\), exact recoverability requires:

\[ H(r) = H(r') \Longrightarrow \boxed{ T_R(r) = T_R(r'). } \]
Full Root reconstruction is required only if the declared Task actually requires full Root reconstruction.

21. Mathematical Root Realization

A proposed Root specification must correspond to an actual mathematical object in the native sector.

\[ \boxed{ \text{Root specification} + \text{receiver} + \text{Passport} + \text{Interface} \longrightarrow \text{actual admissible mathematical instance}. } \]

Failure may occur because:

  • no candidate exists;
  • the receiver domain is empty;
  • the required Interface does not exist;
  • the required quotient/operator/map is undefined;
  • the receiver Passport cannot be satisfied.

22. Mathematical vs Physical Root Realization

\[ \boxed{ \text{mathematical Root realization} \not\Rightarrow \text{physical realization}. } \]

Physical realization additionally depends on:

  • empirically valid physical laws;
  • materials;
  • scales;
  • initial and boundary conditions;
  • causality;
  • stability;
  • implementation constraints.

23. Conservative Obligations on Roots

BM does not need a new intrinsic species called a “Conservative Root.” Instead, conservation is represented as a Root-Passport obligation when the native mathematics requires it.

Let

\[ C_X: X \to V, \qquad C_R: A_R(B_r) \to V. \]

Preservation may require:

\[ \boxed{ C_R(F(x)) = C_X(x). } \]
Root, Passport, Rooting, or Rebranching terminology cannot manufacture a conservation law. Conservation must already follow from the native mathematics.

24. Root Chains

A serial chain of Root uses need not be iteration of one self-map.

\[ R_n \in A_n, \qquad F_n: D_n \subseteq A_n \to Y_{n+1}. \]
\[ R_{n+1} = F_n(R_n). \]

Lawfulness requires:

\[ \boxed{ R_n \in D_n, \qquad R_{n+1} \in A_{n+1}. } \]
A Root chain need not have one fixed state space, one fixed map, a fixed point, or a time parameter.

25. Repeated-Use Self-Maps

Ordinary iteration appears only when an actual self-map is defined:

\[ \boxed{ F: D_F \subseteq X_R \to X_R. } \]

A sufficient all-time invariant region is

\[ \boxed{ S \subseteq D_F, \qquad F(S) \subseteq S. } \]
\[ \boxed{ \text{Root reuse} \not\Rightarrow \text{iteration}. } \]
Once such a self-map exists, its dynamics are ordinary dynamical-systems mathematics.

26. Iteration-Domain Firewall

One lawful application of a Root-processing map does not guarantee that a second application is defined.

\[ R_1 = F(R_0) \]

requires

\[ R_0 \in D_F. \]

But

\[ R_2 = F(R_1) \]

additionally requires

\[ \boxed{ F(R_0) \in D_F. } \]
\[ \boxed{ \text{one-step validity} \not\Rightarrow \text{iterability}. } \]

27. Fixed Points, Cycles, and Stability

Once a genuine repeated-use self-map

\[ F: S \to S \]

exists, fixed points are ordinary fixed points:

\[ \boxed{ R_* = F(R_*). } \]

Periodic points satisfy

\[ F^p(R_*) = R_*. \]

In a differentiable finite-dimensional setting, ordinary local stability theory may use

\[ \rho \left( J_F(R_*) \right) < 1 \]

as a sufficient local asymptotic-stability condition.

  • Fixed-point existence is not implied by Roothood.
  • Stability is not implied by Roothood.
  • Periodic behavior belongs to the actual map \(F\).
  • Non-Euclidean sectors require native stability mathematics.

28. Root Convergence Firewall

BM never infers convergence merely because Root states are repeatedly produced.

\[ \boxed{ R_n \to R_* \]

requires a declared convergence structure.

Depending on the native sector this may mean:

  • metric convergence;
  • norm convergence;
  • weak convergence;
  • weak-* convergence;
  • operator convergence;
  • order convergence;
  • convergence in probability;
  • another native notion.
\[ \boxed{ \text{iteration} \not\Rightarrow \text{convergence}. } \]

29. Model-Specific Root Quantities

The following words have no universal Root-theoretic meaning:

  • Root production rate;
  • Root resistance;
  • Root threshold;
  • Root saturation;
  • continuous Root activity;
  • finite-time Root-event accumulation.

They become mathematics only after a particular model defines the required quantity.

Example: event rate

\[ \Delta t_n = t_{n+1} - t_n, \qquad \nu_n = \frac{1}{\Delta t_n}. \]

Example: threshold

\[ H(x) \ge H_c. \]

Example: finite-time accumulation

\[ \sum_{n=0}^{\infty} \Delta t_n < \infty. \]
These formulas belong to the individual model. BM supplies no universal Root rate, threshold, resistance, saturation, or event law.

30. Candidate Rooting

Status: Candidate.

Rooting is reserved for a more specific attachment operation than ordinary Root reuse or re-entry.

\[ \boxed{ \mathcal A: D_{\mathcal A} \subseteq A_{\mathrm{attach}} \times A_R(B_r) \to X'. } \]

A candidate Rooting event requires:

  • a typed attachment object or site;
  • a mathematically defined attachment Operation;
  • an admissible input pair;
  • law/Passport/Interface compatibility;
  • an admissible resulting mathematical structure.
\[ \boxed{ \text{Root reuse} \not\Rightarrow \text{Rooting}. } \]
Graphical proximity, verbal analogy, or shared notation does not establish a Rooting operation.

31. Candidate Attachment Site

An attachment site is whatever native mathematical object the attachment Operation actually uses.

It may be:

  • a point;
  • a node;
  • a boundary;
  • a subobject;
  • a parameter locus;
  • a morphism;
  • a state;
  • a geometric region;
  • another sector-specific object.
\[ a \in A_{\mathrm{attach}}, \qquad r \in A_R(B_r). \]

Lawful attachment requires:

\[ \boxed{ (a,r) \in D_{\mathcal A}. } \]
Ambient membership alone is not sufficient.

32. Candidate Rebranching

Status: Candidate.

Rebranching is candidate terminology for genuinely new Branch development after lawful attachment or re-entry.

Suppose

\[ x' = \mathcal A(a,r). \]

A later Operation

\[ J_k: D_{J_k} \to Z_k \]

may generate new development when

\[ x' \in D_{J_k}. \]

But separate Branch status must still satisfy the BM Branch-essentiality criterion.

\[ \boxed{ \text{Rooting} \not\Rightarrow \text{Rebranching}. } \]

33. Candidate Seed-to-Root Path

Status: Candidate.

If the Seed structure is used, it requires an actual state space, generative update, admissibility rule, and export condition.

\[ S_0 \xrightarrow{G} S_1 \xrightarrow{G} \cdots \xrightarrow{\text{export condition}} Y. \]

The export condition produces a Response candidate.

Roothood still requires a separate receiver gate:

\[ \boxed{ \text{Seed export} \to \text{Response} \not\Rightarrow \text{Root}. } \]
  • Not every Root comes from a Seed.
  • Ordinary initial data is not automatically a Seed.
  • Seed terminology does not replace the actual generative mathematics.

34. Root Failure Modes

Failure Meaning
Response-only A mathematical output exists but no receiver Root gate has been established.
Applicability failure The export is not even in the Root Passport domain.
Passport rejection The export is a valid candidate type but fails receiver obligations.
Domain failure The Root cannot enter the proposed downstream Operation.
Law/regime failure Required active-law context is absent or inconsistent.
Witness/coupling failure Required shared or coupled witness data do not exist.
Invariant failure A native invariant required by the receiver is not preserved.
Interface failure The export and receiver cannot be lawfully connected.
Continuation failure The Root representation lacks information needed by later mathematics.
Re-entry failure A valid Root for one receiver does not satisfy the next receiver.
Iteration failure A repeated-use self-map leaves its own domain or violates later gates.
Attachment failure A candidate Rooting pair lies outside the attachment Operation domain.
Stale certification Upstream repair modified data on which Roothood depended.

35. Worked Examples

Example A — Receiver-relative scalar Root

\[ r=8. \]

Receiver \(B_1\):

\[ A_R(B_1) = [0,10]. \]

Receiver \(B_2\):

\[ A_R(B_2) = [0,5]. \]

Therefore:

\[ \boxed{ 8 \text{ is Root for }B_1, } \]
\[ \boxed{ 8 \text{ is not Root for }B_2. } \]

Example B — Root reuse without Rooting

Suppose

\[ r=4 \]

is accepted by a receiver whose next Operation is

\[ G(r) = \sqrt r. \]

Then:

\[ G(4)=2. \]

This is ordinary lawful Root reuse.

\[ \boxed{ \text{No attachment structure is required.} } \]

Example C — Genuine repeated-use map

Let

\[ F(R) = \frac12R+1. \]

Then the fixed point satisfies

\[ R_* = \frac12R_*+1, \]

hence

\[ \boxed{ R_*=2. } \]

Iteration gives

\[ R_n = 2 + 2^{-n} (R_0-2), \]

and therefore

\[ R_n \to 2 \]

in the ordinary Euclidean topology.

The convergence belongs to this affine map and topology, not to Roothood.

Example D — Root information loss

Suppose a Response is

\[ Y=(x,y). \]

The first receiver needs only \(x\), so

\[ E_1(x,y)=x. \]

A later receiver needs

\[ T_2(x,y)=x+y. \]

Then \(E_1\) is sufficient for the first receiver but not the second.

\[ \boxed{ \text{Root sufficiency is scope- and receiver-relative.} } \]

36. Root Registry

Formal Root records may receive stable identifiers:

\[ \boxed{ \mathrm{BM\text{-}R00} - \mathrm{BM\text{-}R99}. } \]

\(R99\) is reserved for the master Root registry.

Field What the record should state
Identifier Stable BM-R identifier.
Status Core role, proved property, conditional property, candidate extension, or application.
Source Tree / Response / Operation that produced the export.
Native type Carrier, units, regularity, and sector semantics where relevant.
Receiver The exact receiver for which Roothood is asserted.
Root Passport Applicability domain and acceptance obligations.
Export The receiver-directed export map.
Re-entry Later Operation domain and receiver conditions.
Provenance Configuration / Tree / version from which the Root certificate follows.
Candidate attachment Only if Rooting is actually defined.
Repeated-use model Only if a genuine self-map or stage-varying Root chain exists.
A registry identifier does not substitute for the mathematical Root gate.

37. Root Status Categories

Status Meaning
Core The receiver-relative Root role itself.
Proved property A property of a particular Root system established under explicit hypotheses.
Conditional Valid only while a stated receiver, domain, law, or Passport condition holds.
Candidate Rooting, Rebranching, Seed, or another unpromoted extension.
Application Domain-specific or physical implementation of Root mathematics.
These status labels do not establish historical novelty or empirical validation.

38. What Root Mathematics Does Not Do

  • A Response is not automatically a Root.
  • A Root is not an intrinsic permanent property of a value.
  • Roothood is always receiver-relative.
  • Roothood is not automatically transitive across receivers.
  • A Root does not create a native law.
  • A Root does not create a conservation law.
  • A Root does not automatically create a Branch.
  • A Root does not automatically define a self-map.
  • A Root does not imply iteration.
  • Iteration does not imply convergence.
  • A Root chain does not imply one fixed state space.
  • Rooting is not ordinary Root reuse.
  • Rooting does not imply Rebranching.
  • Seed export does not automatically produce a Root.
  • Threshold, resistance, saturation, and rate are model-specific.
  • A Root name is not a proof of realizability.

39. Central Root Principle

\[ \boxed{ \begin{gathered} \text{A Tree produces a Response.}\\[4pt] \text{An Export prepares that Response for a specified receiver.}\\[4pt] \text{The receiver Passport determines applicability and acceptance.}\\[4pt] \text{An accepted export occupies the Root role for that receiver.}\\[4pt] \text{Roothood is receiver-relative and not generally transitive.}\\[4pt] \text{A Root may terminate or re-enter later mathematics.}\\[4pt] \text{Re-entry must satisfy the actual next domain and Passport.}\\[4pt] \text{Repeated Root use becomes ordinary iteration only when a self-map exists.}\\[4pt] \text{Fixed points, cycles, stability, rates, thresholds, and convergence}\\ \text{belong to the native model rather than to Roothood itself.}\\[4pt] \text{Rooting, Rebranching, and Seed remain candidate specialized structures.}\\[4pt] \text{No Root terminology creates mathematics that was not actually defined.} \end{gathered} } \]
